# F-010: 로그인 2단계 — 기록을 계정에 저장·불러오기

- 상태: 구현됨
- 작성일: 2026-10-31
- 선행: F-008 (백업 묶음 형식 `buildBackup` / `planRestore`), F-009 (구글·카카오 로그인)
- 관련 파일: `src/App.jsx` (로그인 상태 `user`, 9개 키 저장 effect, 상단 바 프로필), `src/lib/backup.js` (재사용), 새 파일 `src/lib/sync.js`, `src/lib/sync.test.js`, `src/App.css`, `CLAUDE.md` (localStorage 키 표, 설정 안내), 새 파일 `docs/supabase/user_data.sql` (Supabase에 표를 만드는 SQL)

## 목적

지금은 기록이 브라우저에만 있어서 브라우저 데이터를 지우거나 다른 기기에서 열면 기록이 보이지 않는다(실제로 기록이 사라진 일이 있었다). 로그인한 사람의 기록을 Supabase 계정에 자동으로 저장하고, 다른 기기·브라우저에서 같은 계정으로 로그인하면 그 기록을 불러온다. 로그인하지 않으면 지금처럼 이 브라우저에만 저장한다.

## 저장 방식 (설계)

- Supabase에 표 `user_data` 하나를 만든다: 사람마다 한 줄 `{ user_id, data, updated_at }`. `data`에는 백업 파일과 같은 묶음(`{ app, version, exportedAt, data: { 9개 키 } }`)을 그대로 넣는다.
- 보안(Row Level Security): 로그인한 사람은 **자기 줄만** 읽고 쓸 수 있다. 다른 사람의 기록은 볼 수도 바꿀 수도 없다.
- 브라우저에는 지금처럼 9개 키를 그대로 저장한다(오프라인에서도 동작). 계정 저장은 그 위에 더하는 것이다.
- 이 브라우저가 어느 계정과, 언제, 어떤 내용으로 맞춰져 있는지는 새 키 `muselog-sync-meta`에 적는다: `{ userId, syncedAt, hash }`. hash는 마지막으로 맞춘 기록 묶음의 지문(짧은 글자)이다. 지금 기록의 지문이 hash와 다르면 "올리지 못한 변경이 있음(dirty)"으로 본다. 그래서 로그아웃한 동안 고친 기록, 저장에 실패한 기록, 백업으로 불러온 기록도 모두 알아챈다.
- 저장 시각 `updated_at`은 기기 시계가 아니라 서버(Supabase)가 정한다. 기기마다 시계가 달라도 어느 쪽이 새것인지 바르게 비교하기 위해서다.

## 사용자 시나리오

1. 컴퓨터에서 기록을 쓰던 사용자가 처음 로그인하면, 계정이 비어 있으므로 이 브라우저의 기록이 계정에 올라간다. 상단 바에 "계정에 저장됨"이 보인다.
2. 이후 곡을 추가하거나 기록을 남기면 몇 초 안에 자동으로 계정에 저장된다.
3. 휴대폰에서 같은 계정으로 로그인하면, 휴대폰 브라우저가 비어 있으므로 계정 기록을 불러와 컴퓨터와 같은 기록이 보인다.
4. 어떤 브라우저에 로그인 전부터 따로 쓴 기록이 있고 계정에도 기록이 있으면, "계정 기록 불러오기 / 이 기기 기록으로 계정 덮어쓰기" 중 하나를 고르게 한다. 기록이 몰래 덮어써지지 않는다.

## 수용 기준

### 처음 로그인했을 때 (이 브라우저가 이 계정과 맞춰진 적이 없음)

- [ ] AC-1: 계정에 저장된 기록이 없으면, 이 브라우저의 기록(9개 키 묶음)을 계정에 올린다. 화면의 기록은 그대로다.
- [ ] AC-2: 계정에 기록이 있고 이 브라우저가 "비어 있으면"(연습 기록·일정·루틴이 하나도 없고, 연습곡이 없거나 처음 깔리는 예시 곡 3개 그대로) 계정 기록을 불러와 화면을 새로 고친다. 묻지 않는다.
- [ ] AC-3: 계정에도 기록이 있고 이 브라우저도 비어 있지 않으면, 화면 가운데 선택 창이 뜬다. 창에는 계정 기록의 마지막 저장 시각과, 양쪽의 연습 기록·연습곡 개수가 보이고 버튼 두 개가 있다.
  - "계정 기록 불러오기": 이 브라우저의 기록을 계정 기록으로 바꾸고 새로 고친다.
  - "이 기기 기록으로 계정 덮어쓰기": 이 브라우저의 기록을 계정에 올린다.
  - 바꾸기 전에 "지금 이 기기 기록을 백업 파일로 받아 두려면 먼저 '백업 내보내기'를 누르세요." 안내가 창 안에 보인다. 창을 닫을 수 없고 둘 중 하나를 골라야 자동 저장이 시작된다(고르기 전에는 계정에 아무것도 쓰지 않는다).

### 이미 맞춰진 브라우저에서

- [ ] AC-4: 로그인한 상태에서 9개 키 중 하나라도 바뀌면(곡 추가, 기록 저장, 루틴 체크, 메트로놈 설정 등) 마지막 변경 후 2초 뒤에 묶음 전체를 계정에 저장한다. 그동안 상단 바에 "저장 중…", 끝나면 "계정에 저장됨"이 보인다.
- [ ] AC-5: 앱을 열 때(또는 로그인 직후) 계정 기록이 이 브라우저의 마지막 맞춤 시각보다 새것이고 이 브라우저에 올리지 못한 변경이 없으면, 계정 기록을 묻지 않고 불러와 새로 고친다(다른 기기에서 쓴 기록 반영).
- [ ] AC-6: 계정 기록이 더 새것인데 이 브라우저에도 올리지 못한 변경이 있으면(두 기기에서 따로 쓴 경우) AC-3과 같은 선택 창을 띄운다.
- [ ] AC-7: 계정 기록이 새것이 아니고 이 브라우저에 올리지 못한 변경이 있으면 바로 올린다.

### 실패와 로그아웃

- [ ] AC-8: 인터넷이 끊기는 등으로 저장에 실패하면 상단 바에 "저장 실패 · 다시 시도" 가 보이고, 누르면 다시 올린다. 기록은 이 브라우저에 남아 있고, 다음에 앱을 열 때도 다시 올린다(지문이 달라 dirty로 봄).
- [ ] AC-9: 로그아웃하면 자동 저장이 멈추고 상단 바의 저장 상태가 사라진다. 이 브라우저의 기록은 지우지 않는다.
- [ ] AC-10: 다른 계정으로 로그인하면 그 계정 기준으로 AC-1~3을 다시 판단한다(앞 계정의 맞춤 정보는 쓰지 않는다).
- [ ] AC-11: 로그인하지 않았거나 Supabase 키가 없으면 지금과 똑같이 동작하고, 계정에 아무것도 보내지 않는다.

### 보안과 서버 설정

- [ ] AC-12: `docs/supabase/user_data.sql`에 표 만들기와 보안 규칙(RLS: `auth.uid() = user_id`일 때만 읽기·쓰기·고치기)이 들어 있다. 사용자가 Supabase SQL Editor에서 한 번 실행한다.
- [ ] AC-13: 코드는 Supabase 공개(anon/publishable) 키만 쓰고, 관리자 키(service_role/secret)는 어디에도 쓰지 않는다.

### 공통

- [ ] AC-14: 판단 로직은 순수 함수로 `src/lib/sync.js`에 둔다: `isEmptyData(data)`(비어 있는지), `decideSync({ cloud, meta, userId, localData })`(→ `"upload" | "download" | "ask" | "none"`), `normalizeSyncMeta(value)`. `src/lib/sync.test.js`에 테스트를 추가한다(처음 로그인 3가지, 맞춰진 뒤 4가지, 다른 계정, 깨진 메타).
- [ ] AC-15: `muselog-sync-meta`는 백업(`BACKUP_KEYS`)에 넣지 않는다. 백업 불러오기를 하면 그 내용이 다음 자동 저장 때 계정에 올라간다(지문이 달라 dirty로 봄).
- [ ] AC-16: 6개 탭과 백업, 로그인/로그아웃이 이전과 같이 동작하고, 좁은 화면에서 저장 상태 표시와 선택 창이 화면 밖으로 넘치지 않는다.
- [ ] AC-17: `npm test`, `npm run build`, `npm run lint`가 오류 없이 끝난다. (lint 경고는 기존 개수보다 늘지 않는다)

## 비범위

- 두 기기 기록을 항목별로 합치기 (이번엔 둘 중 하나 고르기만)
- 앱을 켜 둔 채 다른 기기의 변경을 실시간으로 받기 (앱을 다시 열거나 새로고침할 때 반영)
- 기록 변경 이력·되돌리기, 회원 탈퇴 시 서버 기록 삭제 화면
- 네이버 로그인, 구글 앱 게시(개인정보처리방침 페이지)

## 데이터 영향

| 항목 | 내용 |
|---|---|
| 사용하는 localStorage 키 | 9개 키 (읽기 / 계정 기록을 불러올 때 쓰기), 새 키 `muselog-sync-meta` `{ userId: 문자열, syncedAt: 서버 ISO 시각, hash: 기록 묶음 지문 }` (읽기 / 쓰기) |
| 데이터 구조 변경 | 9개 키의 구조는 그대로. 새 키 1개 추가. 서버(Supabase)에 표 `user_data(user_id uuid PK, data jsonb, updated_at timestamptz)` 추가 |
| 마이그레이션 | 필요 없음. `muselog-sync-meta`가 없으면 "처음 로그인"으로 보고 AC-1~3을 따른다. 깨진 값도 없음으로 읽는다(`normalizeSyncMeta`). 계정에서 불러온 기록은 백업 불러오기와 같은 길(`planRestore` → 새로고침 → 각 normalize 함수)로 들어가므로 예전 형식도 지금 형식으로 읽힌다 |
| 외부 서비스 | 로그인한 사람의 연습 기록 전체가 Supabase(서울 지역)에 저장된다. 본인만 읽을 수 있다 |

## 사용자가 직접 할 일

1. Supabase 대시보드 → SQL Editor에서 `docs/supabase/user_data.sql` 내용을 붙여 넣고 Run (한 번만)
2. (선택) 혹시 모를 일에 대비해 지금 쓰는 브라우저에서 "백업 내보내기"로 파일을 받아 두기

## 확인 방법

- 자동: `npm test`, `npm run build`, `npm run lint`
- 수동 (브라우저):
  1. SQL 실행 후 `npm run dev`, Edge에서 로그인 → "계정에 저장됨"이 보이는지, Supabase Table Editor의 `user_data`에 한 줄이 생겼는지 본다.
  2. 곡을 추가하고 2초 뒤 "계정에 저장됨"이 다시 보이는지, Table Editor의 `updated_at`이 바뀌는지 본다.
  3. 다른 브라우저(또는 InPrivate 창)에서 같은 계정으로 로그인 → 같은 기록이 보이는지 본다.
  4. 그 창에서 기록을 하나 추가 → 첫 창을 새로고침하면 그 기록이 보이는지 본다.
  5. 로그인 전에 따로 기록을 쓴 브라우저에서 로그인 → 선택 창이 뜨는지, 두 버튼이 각각 맞게 동작하는지 본다.
  6. 개발자 도구에서 오프라인으로 바꾸고 기록 추가 → "저장 실패"가 보이는지, 온라인으로 바꾸고 "다시 시도"로 저장되는지 본다.
  7. 로그아웃 → 저장 상태가 사라지고 기록은 그대로인지 본다.
