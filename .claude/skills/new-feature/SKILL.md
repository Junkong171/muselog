# 새 기능 명세 작성과 승인

요청한 기능: $ARGUMENTS

이 절차가 끝나기 전에는 `src/`의 코드를 수정하지 않는다.

## 1. 현재 상태 파악

1. `CLAUDE.md`의 규칙과 localStorage 키 표를 확인한다.
2. 관련 코드를 읽는다. 추측하지 말고 실제 코드(`파일:줄`)를 근거로 한다.
3. 작업 브랜치인지 확인한다. main이면 사용자에게 새 브랜치 이름을 제안하고 승인받는다.

## 2. 명세 파일 만들기

1. `docs/specs/`에서 가장 큰 F 번호를 찾아 다음 번호를 쓴다. (예: F-001 다음은 F-002)
2. `docs/specs/_TEMPLATE.md`를 바탕으로 `docs/specs/F-xxx-<짧은-영문-이름>.md`를 만든다.
3. 모든 항목을 채운다.
   - 수용 기준은 눈으로 보거나 명령으로 확인할 수 있는 문장으로 쓴다.
   - 데이터 영향: localStorage 키나 구조가 바뀌면 마이그레이션 방법을 반드시 쓴다.
   - 비범위: 이번에 하지 않을 것을 분명히 쓴다.
4. 상태는 "초안"으로 둔다.

## 3. 사용자에게 보여주기

한국어로 다음을 보여준다. 어려운 용어에는 짧은 풀이를 붙인다.

1. 명세 파일 경로
2. 목적과 수용 기준 목록
3. 데이터 영향 (특히 기존 사용자 데이터가 깨질 가능성)
4. 바꿀 파일과 대략적인 변경 내용
5. "이대로 진행할까요?" 질문

## 4. 승인 후

1. 사용자가 승인하면 명세의 상태를 "승인됨"으로 바꾼다.
2. 수정 요청이 있으면 명세를 고치고 3단계를 다시 한다.
3. 구현이 끝나면 `/verify-feature docs/specs/F-xxx-....md`로 검증한다.
